# pico 多 Agent 协作优化 v2：信息共享与实时重规划

> 状态：已实现（v2.1–v2.4）。基于已落地的 v1（见 `multi-agent-v1-design.md`）。测试见 `tests/test_orchestration_collab.py`。
> 目标：解决两个问题——(A) 组员之间如何讨论、传递信息；(B) 组长如何根据实时进度修改方案。
> 前提不变：单进程、零第三方依赖、同步 IO、文本工具协议，Windows/Linux/macOS 都能跑。

每节仍分三块：**设计** / **💬 白话解释** / **📖 本节术语**。

---

## 0. 先说清楚边界：同步单进程下什么能做、什么不能做

pico 是单进程、同步的：一个 agent 的主循环在"调用模型 → 等结果 → 执行工具"之间是**阻塞**的。它自己不占线程时做不了别的事。这决定了：

- **做得到**：子 agent 并行跑在线程里；它们通过一块共享数据区交换信息；组长在每一小批任务之间重新决策。
- **做不到（本版不做）**：两个正在跑的组员之间**实时双向对话**（A 问一句、停下等 B 答、B 再答）。在同步模型里这需要阻塞等待,一旦互等就死锁。组长也无法在一个组员**正跑到一半时**改它的任务书——只能在批次之间调整，或直接中止它。

所以 v2 的思路是:**不让组员直接对话，而是通过"共享黑板 + 异步信箱 + 向上提问"交换信息；组长的"实时"= 把调度切成小批，在每批之间看进度、改计划。** 这样既拿到用户想要的协作效果,又守住 v1 的三条不变量:可审计、不死锁、预算可控。

> 💬 **白话解释**
> 想象一个开放式办公室,但规定"工作时不许交头接耳"。原因是:只要允许面对面你问我答,就可能出现"我等你回话、你等我回话",两个人僵在那——在 pico 这种"一次只能干一件事"的程序里,这种僵局会真的卡死。
> 替代办法有三个,都不需要"停下来等对方":① 一面**公告墙**(黑板),谁有结论就贴上去,别人路过自己看;② 一个**收件箱**,你可以给别人留张条子,但留完就继续干自己的,不等回信;③ 实在卡住缺信息,就**举手问组长**,由组长去协调,而不是自己扭头问隔壁。
> 组长的"实时调整"也一样:他没法在你打字打到一半冲进来改你的活,但他可以**每过一小会儿**(每跑完一小批)就看一眼墙上的进度,然后决定下一步派谁、停谁、改什么。

> 📖 **本节术语**
> - **阻塞**:程序执行到某一步会原地等待(比如等模型 API 回复),等待期间什么都做不了。
> - **死锁**:两方互相等待对方先完成,结果谁都动不了。
> - **线程**:同一个程序里可以同时推进的执行流;pico 让子 agent 跑在各自线程里实现并行。
> - **不变量**:系统在任何情况下都应保持成立的性质,这里指"可审计、不死锁、预算可控"。

## 第一部分 (A)：组员之间如何共享信息

三种机制,从"松"到"紧":黑板(广播)、信箱(定向)、向上提问(求助)。全部**非阻塞**。

### A1. 共享黑板 Blackboard（广播式，所有角色可读写）

**设计**
- 新工件 `.pico/runs/<run_id>/blackboard.json`:一个**只追加**的条目列表。
- 条目结构:
  ```json
  {"id":"n7","from_task":"t2","kind":"finding|decision|interface|warning",
   "key":"api.signature","text":"estimate_tokens(text)->int","evidence":"pico/context_budget.py:40",
   "created_at":"2026-10-14T...Z"}
  ```
- 给子 agent（worker/explorer/reviewer 都可）新增两个**安全**工具(不涉及编排,不会让子 agent 越权):
  - `post_note(key, text, evidence="")`:向黑板追加一条。
  - `read_notes(key_prefix="")`:按 key 前缀读回条目（空前缀=全部，带上限+按新鲜度截断）。
- 由 Orchestrator 持有黑板,内存结构 + 一把锁保证线程安全,每次追加原子落盘。子 agent 的工具调用通过回调写进这块共享区。

**为什么是黑板而不是直连**
- 只追加 → 完整可审计(谁在什么时候贴了什么,一目了然)。
- 读是非阻塞的 → 不可能死锁。
- 仍是星型:大家对着"墙"说话,不是互相喊话,决策权仍在组长。

**典型用法**:worker t2 实现了某函数,`post_note("api.add_budget.signature", "build_budget_profile(window, max_new_tokens)->BudgetProfile")`;并行的测试 worker t3 开工时 `read_notes("api.add_budget")` 就能拿到签名,不必猜或重读。

### A2. 异步信箱 Mailbox（定向留言，非阻塞）

**设计**
- board 上每个 task 增加 `inbox: []`。
- 子 agent 新增工具 `send_message(to_task, text)`:向目标任务的收件箱投一条,**投完立即返回**,不等回复。
- 收件箱投递是"拉"模型:子 agent 在每一步可用 `check_inbox()` 读取发给自己的新消息(读过的标记已读)。
- 不保证时序(并行时谁先投达取决于调度),所以只适合"留个信息",不适合"我必须等你回答"。要等回答的场景走 A3。

**典型用法**:主要有两类真正有用的场景——(1) 一个 worker 给**还没开始**的下游任务留话(下游开工时在 inbox 里看到);(2) 组长/监工给**正在跑**的某个 worker 递一条提示(配合第二部分的中途介入)。并行同时开工的两个 worker 之间,信箱价值有限(它们起点相同、各自带着固定 Brief),这点要如实说明。

### A3. 向上提问 Ask-up（阻塞类需求的安全替代）

**设计**
- Result 增强:子 agent 若因缺信息干不下去,返回 `status: "blocked"` + 新字段
  ```json
  "needs":[{"question":"t1 用的是哪个配置键?","suggested_source":"t1 或 config.py"}]
  ```
- Orchestrator 收到后三选一路由:① 直接从黑板/依赖结果里找到答案;② 派一个 explorer 快速查;③ 把它并入重规划(第二部分)。有答案后用新工具 `answer_need(task_id, text)` 把答案写入该任务,下次重试时答案进 Brief。

**为什么"向上问"而不是"横向问"**:横向问 = 组员 A 停下等组员 B,正是会死锁的那种阻塞等待。向上问把"等待"交给组长在**批次之间**消化,组员本身永远不阻塞。

> 💬 **白话解释**
> - **黑板**:公告墙。谁有了确定的结论(比如"这个函数就叫这个名、收这几个参数")就贴一张,带上"证据在哪个文件第几行"。别人要用自己去看,不用打扰贴的人。墙上只增不改,所以事后能查清每条是谁几点贴的。
> - **信箱**:给某个人留的便利贴。你写完贴上就走,不站在那等他看。他下次干活时顺手翻一下自己的信箱。适合"告诉你一声",不适合"我等你回复"。
> - **向上提问**:真卡住了、缺的信息自己弄不到,就在交回的报告里写一句"我需要知道 X",然后这一轮先停。组长看到后帮你把 X 找来(从墙上找、或派个人去查),下次再派你时就把答案一起给你。关键是:**你从不原地等别人**,等待这件事交给组长在空档期处理。

> 📖 **本节术语**
> - **只追加 (append-only)**:只能往末尾加新条目,不能改也不能删已有条目;天然适合做审计记录。
> - **原子落盘**:先写临时文件再整体替换,保证文件任何时刻要么是旧的完整版、要么是新的完整版。
> - **拉模型 (pull)**:信息放在那儿,需要的人主动来读;对应"推模型"是系统主动塞给你。
> - **路由**:把一个请求转交给合适的处理方。
> - **Brief / Result**:v1 定义的父给子的"任务简报"和子回父的"结构化报告"。

## 第二部分 (B)：组长如何根据实时进度修改方案

核心改动:把 `run_tasks` 从"把所有就绪任务一次跑完"改成"**跑一小批就把控制权还给组长**",组长在批次间看进度、下达计划增量。

### B1. 小批调度 + 事件早返回

**设计**
- `run_tasks(selector, mode)` 增加 `mode`:
  - `mode="wave"`(新默认):只跑**一波**就绪任务(最多 `max_concurrency` 个),这波全部结束就返回。
  - `mode="all"`(v1 旧行为):反复跑到无就绪任务,保持兼容。
- 并且在一波内发生**可操纵事件**时也会在该波结束后立即返回,不再自动开下一波:任务终态失败、`scope_violation`、worker 返回 `blocked+needs`、预算越过阈值。
- 这样组长每过"一小批"就能重新决策。真·"跑到一半插手"在同步模型里做不到(见第 0 节),能做到的是"每小批之间插手",粒度由批大小控制。

### B2. 进度摘要 Progress Digest

**设计**:`run_tasks` 返回结构化进度,而不只是看板文本:
```json
{"completed":["t1"],"failed":[{"id":"t2","reason":"verify_failed","error":"..."}],
 "blocked":[{"id":"t3","needs":[...]}],"ready_next":["t4"],
 "budget":{"used_steps":12,"max":120,"used_tokens":...},
 "blackboard_recent":[{"key":"api.sig","from":"t1"}]}
```
组长据此判断下一步,不用自己去翻看板和黑板。

### B3. 计划增量操作（plan deltas）

**设计**:在已有 `plan_tasks`(可增改 pending 任务)基础上,补齐明确的动词,让"改方案"意图清晰、可审计:
- `amend_tasks(tasks)`:新增任务,或修改仍是 pending/blocked 任务的规划字段(目标、验收、写范围、依赖)。
- `cancel_tasks(ids, reason)`:取消任务。pending → 直接 cancelled;**running → 通过 cancel_event 抢占**(worker 在下一步开头检查到信号即停)。
- `answer_need(task_id, text)`:回答被 blocked 的任务(见 A3),并把它放回 pending。
- 已 done 的任务不可改(其产物可能已被下游依赖),只能新增补救任务。

### B4. 中途抢占（唯一的"任务进行中"介入）

**设计**:组长读了某 worker 贴在黑板上的中间结论,发现方向错了,可以 `cancel_tasks([t5], reason="approach wrong, replanning")` 立即止损,再 `amend_tasks` 换个更明确的 Brief 重开。这是同步模型下唯一能对"正在跑的任务"做的实时干预——**停,但不能改**。

### B5. 组长主循环（提示词层面的策略）

写进 Orchestrator 的系统提示,形成闭环:
```
plan_tasks → run_tasks(mode="wave") → 读 digest
  → 有 blocked？answer_need 或派 explorer
  → 有 failed？amend_tasks 调整后重试，或 cancel 止损
  → 发现更优路径？amend/cancel 改计划
  → 预算紧张？收缩后续任务
  → 还有 ready？继续 run_tasks(mode="wave")
直到看板清空或预算耗尽
```

> 💬 **白话解释**
> v1 里组长像"派完活就去睡觉,全干完才醒"。v2 把它改成"派一小批、守在旁边,这批一完就看一眼仪表盘,再决定下一步"。
> 仪表盘(进度摘要)上写着:谁干完了、谁失败了为什么、谁卡住了缺什么、还有谁待命、预算还剩多少、墙上最近贴了什么。组长看完可以:给卡住的人补上答案、把失败的活改改重派、发现有人跑偏了当场叫停换方案、钱不够了就砍掉后面的活。
> 唯一的限制还是那条:他不能在你打字打到一半改你的任务书。他能做的是**叫停**你(你下一步一抬头就看到"停"的信号),然后重新给你一张新任务书。所以"实时"在这里是"每一小批之间",批越小、他介入越勤。

> 📖 **本节术语**
> - **一波 / 小批 (wave)**:一次并行跑的一组就绪任务,最多 `max_concurrency` 个。
> - **可操纵事件 (steering event)**:值得组长立刻介入的情况——失败、越界、卡住、预算告警。
> - **抢占 (preempt)**:在一个正在运行的任务自然结束前把它中止。
> - **cancel_event**:v1 已有的"停止信号";子 agent 每轮开头检查,置位就停机。
> - **计划增量 (plan delta)**:对现有计划的局部改动(加/改/删任务),相对"从头重排整个计划"。

## 第三部分：怎么接进现有代码

**新增工件**
- `.pico/runs/<run_id>/blackboard.json`(只追加)。
- board 的 task 增加 `inbox: []`;Result schema 增加 `needs: []`。

**子 agent 新增安全工具**(注入给 worker/explorer/reviewer,**不含编排权**,所以不破坏"委派深度≤1"):
`post_note` / `read_notes` / `send_message` / `check_inbox`。

**Orchestrator 新增/改动工具**(仅顶层):
`run_tasks(mode)`、`cancel_tasks`、`amend_tasks`、`answer_need`;`run_tasks` 返回进度摘要。

**调度层**(`orchestrator.py`):
- `_schedule` 已是 wave 循环,改成 `mode="wave"` 时跑完一波即返回;事件早返回在 `_apply_outcome` 后判定。
- 新增 `Blackboard` 类(内存 list + `threading.Lock` + 原子落盘),把 `post_note/read_notes/send_message/check_inbox` 作为回调注入子 agent;读取在子 agent 执行线程内发生,写入走锁。

**不变量怎么守住**
- 组员之间无直接阻塞调用 → 不死锁。
- 黑板只追加 + 加锁 + 原子写 → 可审计、线程安全。
- 组长仍是唯一规划者 → 星型拓扑不破(组员只共享数据,不夺决策权)。
- 预算账本不变,仍全程生效。

**风险与取舍**
- 并发贴黑板带来非确定性:条目带时间戳 + key,回归测试用 `concurrency=1` 保证确定性。
- 黑板撑大上下文:注入子 agent 的条目数设上限并可按 key 过滤。
- `send_message` 在并行同起的 worker 间价值有限:如实说明,主用于"留给下游"和"组长递话"。
- "实时"的真实含义是"每小批之间",不是"任务进行中":这是同步单进程的硬边界,批越小粒度越细,代价是组长被唤醒越频繁、token 花得越多。

## 第四部分：建议的实施顺序

| 阶段 | 内容 | 状态 |
|---|---|---|
| **v2.1 黑板** | `Blackboard` 类（`orchestration/blackboard.py`）+ `post_note`/`read_notes`，经 `CollabHandle` 注入子 agent，落盘 `blackboard.json` | ✅ 已实现 |
| **v2.2 小批调度 + 进度摘要** | `run_tasks(mode="wave")` 默认一波即返回 + `_digest` 结构化进度摘要 | ✅ 已实现 |
| **v2.3 计划增量** | `amend_tasks` / `cancel_tasks`（pending 直接取消、running 经 cancel_event 抢占、依赖级联）/ `answer_need` + Result 的 `needs` 字段 | ✅ 已实现 |
| **v2.4 信箱** | `inbox` + `send_message` / `check_inbox` | ✅ 已实现 |

落地与本稿的差异：
- 权限修复：协作工具（黑板/信箱）是能力无关的内建工具，`tool_executor.execute()` 的白名单校验改为以 `agent.tools`（含协作工具）为准，而不是角色的原始 `allowed_tools`，否则会误拒 `post_note`/`read_notes`。
- `amend_tasks` 复用 `plan_tasks` 的“增改 pending/blocked 任务”语义，未另起炉灶。
- 测试：`tests/test_orchestration_collab.py`（10 个用例，含黑板身份与并发安全、信箱消费一次、needs/answer_need、wave 摘要、cancel 级联），随主套件全绿（186 passed）。

每阶段都能单独测试、单独合入，与 v1 全绿套件并存。

## 一句话总结

> **组员不直接对话(会死锁),而是通过"只追加的共享黑板 + 非阻塞信箱 + 向上提问"交换信息;组长的"实时改方案"= 把调度切成小批,在每批之间读进度摘要、下达计划增量,并可中止(但不能改写)正在跑的任务。** 这样拿到了协作与适应能力,同时守住 v1 的可审计、不死锁、预算可控。
